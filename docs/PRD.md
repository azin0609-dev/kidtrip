## 1. 產品定位

**一句話：**幫有 0–6 歲小孩的家庭，每週五分鐘內決定週末去哪玩。

**第一個使用者：**我們家。住新北林口，老大 3 歲、老二還在推車階段，兩個大人都會用。

**要解決的痛：**
- 每週都要重想一次，資料散在各個部落格。
- 到現場才發現：沒開、下雨、太遠、設施不適合小小孩、推車推不動。
- 夫妻各自查、各自收藏，資訊沒有同步。

**成功的樣子：**週四晚上打開 App，看到三個推薦，兩個人花五分鐘選一個，週末直接按導航出發。

---

## 2. 核心循環

1. 週四、週五打開，看到「這週推薦 3 個」（會參考天氣、車程、去過的地方）。
2. 夫妻在各自手機看到同一組推薦，一起挑一個（Phase 2 起同步）。
3. 週末按「導航」出發，App 提醒建議出發時間，讓回程剛好接上午睡（Phase 2）。
4. 回家後打卡、評分，集章護照多一格（Phase 2）。
5. 下次推薦更貼近這個家庭的喜好。

## 4. Phase 1 — MVP（純前端 PWA，不需要任何金鑰）

部署在 GitHub Pages，跟 Oliver 英文 App 同一種做法。沒有後端，資料存在使用者自己的瀏覽器。

### 任務 1-1：專案骨架與資料層
- 建立 Vite + React + TypeScript（strict）+ Tailwind 專案。
- 依照第 7 節寫出 `Spot`、`Hotel` 的 TypeScript 型別，在建置時 import `data/*.json`。
- `npm run validate:data`：用 zod 檢查資料。檢查項目：
  - 必填欄位、enum 值合法（region、types、env、cost_tier、tags、price_tier）。
  - `id` 不重複。
  - `near_spot_ids` 都能在 spots.json 找到。
  - `opens_on`、`closes_on` 是合法日期（YYYY-MM-DD）。
  - `mins_from_linkou` 是正整數。
  - 有錯就列出 id 與原因，結束碼非 0。
- 設定 ESLint、Vitest，加上 GitHub Actions CI（lint、typecheck、test、validate:data）。
- 一頁最簡單的畫面：顯示「景點 75 個、飯店 30 間」，證明資料讀得到。

**驗收標準**
- [ ] `npm run dev` 能啟動，畫面顯示正確的景點、飯店數量。
- [ ] 故意把某筆 `region` 改成 `"西"`，`validate:data` 會失敗並指出是哪一筆。
- [ ] CI 在 push 後全綠。
- [ ] 沒有寫死任何景點資料在元件裡。

### 任務 1-2：清單、篩選、收藏
照目前原型（claude.ai 上的「這週去哪玩」頁面）的功能做出正式版：

- 分頁：親子景點／親子飯店／我的收藏，用網址 hash 記住分頁。
- 景點篩選：
  - 車程：全部、30 分內、1 小時內、2 小時內、要住一晚（> 120 分）。
  - 地區：北、中、南、東。
  - 條件開關：下雨也能玩（env 為 in 或 semi）、免費、推車好推、隱藏去過的。
  - 類型：多選，符合任一類型就顯示。
- 飯店篩選：車程、地區、設施標籤（多選）。
- 搜尋：比對名稱、城市、說明、類型名稱、飯店特色；空白分隔多個關鍵字，全部都要符合。
- 預設依車程由近到遠排序。
- 卡片內容：名稱、城市、車程大數字、標籤（室內外、費用、推車、類型、badge）、一句建議、附近可住（景點卡）／順遊（飯店卡）。
- 卡片按鈕：Google Maps（導航連結）、收藏、去過（飯店卡改成「查房價」＋收藏）。
- 收藏、去過存在 localStorage，key 為 `kidtrip.v1`，讀寫都要 try/catch，壞掉時畫面照常運作。
- 「幫我抽一個」：從目前篩選結果隨機抽，優先排除去過的，不要連續抽到同一個。
- 日期規則（用 Asia/Taipei 判斷「今天」）：
  - `closes_on` 已過 → 不顯示。
  - `closes_on` 在 21 天內 → 顯示「X/X 熄燈」badge。
  - `opens_on` 還沒到 → 顯示「X/X 開幕」badge，抽籤時排除。
- 頁尾固定顯示：資料整理日期、「開放時間與票價以官方公告為準」、車程是粗估。

**驗收標準**
- [ ] 篩選、搜尋、排序寫成純函式，有單元測試。
- [ ] 把系統日期設成 2026-12-01，野趣森林不會出現。
- [ ] 日期設成 2026-11-20，KidZania 顯示「11/24 開幕」，抽籤抽不到它。
- [ ] 收藏後重新整理頁面，收藏還在；清掉 localStorage 也不會出錯。
- [ ] 390px 寬手機版沒有左右捲動，按鈕都按得到。
- [ ] 深色模式文字清楚。

### 任務 1-4：出發地與車程粗估
**座標補齊腳本** `npm run geocode`（只在開發時跑，不在使用者端跑）：
- 對 `lat` 為 null 的景點、飯店，用 OpenStreetMap Nominatim 以「名稱＋城市」查座標。
- 每秒最多 1 次請求，User-Agent 要寫專案名稱和聯絡方式。
- 寫回 `lat`、`lng`，另外產生 `data/geocode-report.md`：列出查不到的、結果離所屬縣市中心太遠的、名稱比對不像的，給我人工檢查。
- 已經有座標的不要覆蓋。
- 另外產生 `data/origins.json`：全台 22 縣市＋368 鄉鎮市區的代表座標，給出發地選單用。

**出發地設定：**
- 預設「新北市林口區」。
- 可以「用目前位置」（使用者按了才要求定位權限，不要一打開就問）。
- 可以從縣市 → 鄉鎮下拉選單選。
- 存在本機。

**車程公式（初版，請用資料校正）：**
- 直線距離 × 道路係數 1.35，再依距離套平均速度：15 公里內 30 km/h、15–60 公里 55 km/h、60–150 公里 75 km/h、超過 150 公里 95 km/h，最後加 5 分鐘。
- 東部景點（region 為「東」）從西部出發要另外加大道路係數，請用資料校正出來。
- 校正方法：以林口為出發地，算出的分鐘數和 `mins_from_linkou` 比較，調整參數。
- 畫面顯示「約 X 分（粗估）」或「約 X.5 小時（粗估）」。

**孩子設定（只存本機）：**暱稱、出生年月（算年齡）、午睡時段（預設 13:00–15:00，Phase 2 用）。

**驗收標準**
- [ ] 以林口為出發地，至少 80% 的景點，公式算出的車程跟 `mins_from_linkou` 誤差在 ±35% 以內（寫成測試）。
- [ ] 換成「高雄市鳳山區」出發，高雄親子遊樂園區排在前面。
- [ ] 拒絕定位權限時有清楚提示，並改用下拉選單。
- [ ] 畫面上有「© OpenStreetMap contributors」標示。

### 任務 1-5：這週推薦 3 個
首頁最上方顯示三張推薦卡，每張附上推薦原因（例如「離家 25 分・室內・上次去是 10 週前」）。

**評分規則（初版，之後可以調）：**
- 排除：已熄燈、還沒開幕、8 週內去過的。
- 車程：60 分內加分最多，60–120 分次之，超過 120 分只在「這週要住一晚」開關打開時才推。
- 新鮮度：沒去過加分，去過越久加越多。
- badge：新開幕加分；21 天內要熄燈的加更多分（最後機會）。
- 收藏過的加分。
- 天氣：Phase 1 先放一個手動開關「這週可能下雨」，打開就只推 env 為 in 或 semi 的。Phase 2 改成自動。

**組合規則：**
- 三個不能都是同一類型。
- 至少一個在 60 分鐘內。
- 同一週結果固定：用「ISO 週數＋出發地」當亂數種子，兩支手機設定相同就看到同一組。
- 有「換一組」按鈕（種子加 1）。

**驗收標準**
- [ ] 評分、組合寫成純函式，有單元測試，包含「8 週內去過不推」「同週結果固定」「三個類型不全相同」。
- [ ] 打開「這週可能下雨」後，三個推薦都是室內或半室內。

## 5. Phase 2 — 全家同步、天氣、午睡、集章（方向）

開工前我會再確認細節。預計技術：Supabase（登入、Postgres、Row Level Security、Edge Functions），前端仍放 GitHub Pages。

- **2-1 帳號與全家共用：**Email 登入連結或 Google 登入。一個「家庭」可以有多位成員，用邀請碼加入。收藏、去過、評分都存在家庭底下，RLS 限制只有成員看得到。第一次登入時，把本機的收藏和去過紀錄搬上去。
  - 注意：Supabase 免費方案的專案一段時間沒人用會被暫停，要確認目前規定。
- **2-2 週末天氣（已於 2026-11-17 提前完成，做法有改）：**實際做法是前端直接呼叫 Open-Meteo 的免費預報（不需要授權碼、不需要後端），只送出四捨五入到小數 1 位的出發地座標，快取 1 小時；週末降雨機率 ≥ 60% 時自動打開「這週可能下雨」，使用者可以手動關掉；畫面標示「天氣預報：Open-Meteo」。以下是原本的規劃，留作日後想換回中央氣象署時參考：
  - 原規劃：Edge Function 代理中央氣象署開放資料（需要免費授權碼，放在伺服器端，不進前端）。用「鄉鎮天氣預報－各縣市未來 1 週」資料集（F-D0047 系列，每個縣市一個代碼）。降雨機率只提供 3 天內，所以從週四起才顯示週末降雨。快取 1 小時。降雨機率 ≥ 60% 時，推薦自動偏向室內。畫面標示「資料來源：中央氣象署」。
- **2-3 午睡友善出發時間：**依車程和午睡時段，建議幾點出發、幾點上車回家，讓回程剛好睡。單程超過 90 分鐘時提醒「建議住一晚」。
- **2-4 集章護照：**打卡後在護照蓋章，依北中南東分頁，有一個給小孩看的大圖模式。
- **2-5 評分：**1–5 分，加上幾個快速標籤（適合 3 歲、好停車、推車好推、會再來）。評分會影響推薦的類型偏好。

## 6. Phase 3 — 對外產品化（方向，要不要做之後再決定）

- **3-1 Google 即時資訊：**資料裡只存 `google_place_id`，使用者點開景點時才透過 Edge Function 向 Google Places API 查今天的營業時間和評分，用 field mask 只拿需要的欄位以控制費用。依 Google 規定，除了 place_id，其他內容不能長期存。要先準備公開的使用條款和隱私權政策頁。
- **3-2 真實車程（選配）：**只對推薦的三個景點呼叫 Google Routes API，設每月費用上限。
- **3-3 資料後台：**景點資料搬到資料庫，做一個只有我能用的管理頁；每張卡片加「回報資訊錯誤」。
- **3-4 城市頁 SEO：**例如「桃園親子景點」頁，需要預先產生靜態頁，屆時評估是否改用 Astro 或 Next.js。
- **3-5 營收：**飯店、門票的聯盟行銷連結，畫面標示「含推薦連結」。不放一般廣告。

## 7. 資料模型

### spots.json 的每一筆
| 欄位 | 型別 | 說明 |
|---|---|---|
| id | string | `spot-001` 格式，發布後不可改 |
| name | string | 名稱 |
| city | string | 縣市＋區，可能帶括號補充（例如「（青埔）」） |
| region | "北" \| "中" \| "南" \| "東" | 地區 |
| types | string[] | park, zoo, farm, theme, sea, museum, indoorplay, train, dino, water |
| env | "in" \| "semi" \| "mix" \| "out" | 室內／半室內／室內＋戶外／戶外 |
| cost_tier | "free" \| "$" \| "$$" \| "$$$" \| "?" | 大人門票級距 |
| stroller_ok | boolean | 推車好推 |
| mins_from_linkou | number | 從林口出發的人工粗估分鐘數，車程公式校正用 |
| tip | string | 給 3 歲小孩家長的一句建議 |
| badge | { kind: "new" \| "end", label: string }? | 選填 |
| opens_on / closes_on | "YYYY-MM-DD"? | 選填 |
| open_note | string? | 選填。公休日、要不要預約之類的一句提醒（例如「週一休館」），卡片上顯示成「出發前注意」。2026-11-17 新增 |
| lat / lng | number \| null | 由 geocode 腳本補上（OSM） |
| google_place_id | string \| null | 只存 ID |
| needs_verify | string[] | 待人工確認的欄位名稱 |
| last_verified | "YYYY-MM-DD" | 最後整理日期 |

### hotels.json 的每一筆
id（`hotel-001`）、name、city、region、price_tier（"$$" \| "$$$" \| "$$$$"）、tags（play, slide, pool, spa, park, animal）、features（string[]）、mins_from_linkou、tip、near_spot_ids、lat、lng、google_place_id、needs_verify、last_verified。

### 本機儲存（Phase 1）
```ts
// localStorage key: "kidtrip.v1"
{ fav: string[]; been: string[]; beenAt?: Record<string, string>; // id → YYYY-MM-DD
  origin?: { label: string; lat: number; lng: number };
  kids?: { nickname: string; birthYm: string }[];
  nap?: { start: "13:00"; end: "15:00" } }
```
`beenAt` 在任務 1-5 加入，用來算「多久沒去」。

## 8. 資料授權與規範（已確認）
- **Google Maps：**導航連結免費可用。Places 等 API 的內容除了 place_id 不能長期存，要用時再即時查。
- **OpenStreetMap：**座標資料採 ODbL 授權，畫面要標示「© OpenStreetMap contributors」。Nominatim 每秒最多 1 次請求。
- **中央氣象署：**政府資料開放授權條款，標示資料來源。（目前沒有使用）
- **Open-Meteo（2026-11-17 新增）：**天氣預報採 CC BY 4.0 授權，畫面要標示來源；免費方案限非商業使用，如果之後要對外營運（Phase 3）要重新評估。
- **隱私：**定位只在使用者按下按鈕時取得；Phase 1 所有個人資料只存在使用者裝置。唯一的例外是查天氣時會把出發地座標四捨五入到小數 1 位（約 10 公里）送給 Open-Meteo。孩子資料只存暱稱和出生年月。
